Both models on the ZedBoard

16 Nov 2026 · modelV2 and the Tiny-TPU RSCL model on the MAC Attack accelerator (mac_attack_accel_MLP) · follows 13 (modelV2) and 14 (its review), which ended with "run it on the board"

Two ML models were connected to the MAC Attack accelerator and run on the ZedBoard: modelV2, the team's frozen bearing-health model (document 13), and the professor's Tiny-TPU RSCL motor-vibration model. Every number the accelerator returned matched the software model exactly, and both board programs passed.

1. The hardware

The accelerator is an 8 × 8 systolic array of INT8 multiply-accumulate units with exact 22-bit sums, built into the ZedBoard's FPGA. Its on-chip MLP controller (mlp_ctrl) runs a whole model of up to 4 layers in one go: it holds each layer's weights, adds the bias, rescales and applies ReLU between layers, and returns the last layer's raw sums. The ZedBoard's ARM processor drives it through AXI4-Lite registers. The committed build runs at 214.286 MHz.

PCTrain, quantize, export weights and test rows as a C header
ARMLoad weights, biases and scales once; send input rows; read the sums
FPGARun every layer in the 8 × 8 array, with the step between layers on chip
ARMCheck every sum against Python; turn the sums into a prediction

2. How each model was connected to the accelerator

Neither model required any change to the RTL. Each one gets an interface: software that converts the trained model into what the accelerator understands, and an ARM program that loads it through the accelerator's registers. Each interface was checked against the RTL in simulation before the board run.

The Tiny-TPU testbench and app live in a copy of the project, mac_attack_accel_MLP_TinyTPU. Its RTL is identical to the original's, so running the app from the original project, as this run did, gives the same results.

One known difference from the professor's contract. His contract caps hidden values at 7, but the chip caps them at 127. On the 12 golden rows the two agree exactly. On 10 of the 52 random rows the on-chip sums differ from the contract's, but the predicted class never does. The on-chip test checks those rows against the chip's own integer path.

  • Exact: all 256 sums matched Python in every batch size. The clock counts, 474 for one row and 1,986 for 64, equal the RTL check recorded before the board run.
  • The bus dominates the time. At 214.286 MHz, 1,986 clocks is about 9.3 µs. The 64-row run took 127 µs, so roughly 93 % of it is the ARM sending data and reading results.

The speedups are inflated. The program was built in Debug (−O0), and it printed that warning itself. That makes the ARM-alone time slower than it should be, so 11.7× to 30.8× is too high. Rerun with the Release build before quoting a speedup.

What the model predicted

The 64 test rows are spaced evenly through the lives of 7 bearings: B02, B03, B04, B08, B09, B11 and B12, in that order. Each recording runs from new to failure. The table shows every row the board printed, with its bearing and how far through that bearing's life it comes.   • All 10 statuses agree with whether damage had started. Healthy rows are at 95–98 % health, and rows after onset at 13–48 %.
  • How health works: each bearing's first measurements set its healthy baseline. Health is 100 % while the vibration score stays within 2.5 times normal noise, and falls on a log scale to 0 % at 25 times, a typical end-of-life level. Within one bearing it only goes down. The jumps back up in the list are where a new bearing starts.
  • B09 (rows 35, 42): damage started early, about 10 % through its life, and grew slowly, so health stays near 48 %.
  • B12 (row 63): its recording stops at moderate damage, not at failure, so it reads "faulty" but still at 76 % health.

These rows test the hardware, not the model's accuracy. They come from the data the final model was trained on. Accuracy comes from bearings the model never saw (documents 13 and 14):

  • Validation (7 bearings): damage caught on 7 of 7, no false alarms. Health error is 3–9 points before onset and 6–20 points after.
  • Locked test (4 bearings, run once): damage caught on 4 of 4, 0 false alarms in 600 healthy rows. Health error is 3–5 points before onset. After onset it's 5–12 points on B07, B13 and B17, and 51 on B06.

The fault alarm is the stronger output. Health % is reliable while a bearing is healthy and a rough guide once damage has started.

What this model's predictions mean. The model only says healthy or faulty; it has no health %. It was trained on the professor's synthetic demo vibrations, and all 12 golden rows are "healthy". This run proves the arithmetic on the board, but it says nothing yet about real motors. That needs training on the University of Ottawa recordings first.

5. What's next

  • Rerun MAC_model_V2 with the Release build to get a fair speedup figure.
  • Run both models on the Tiny-TPU V2 chip RTL (tinytpu/fpga_zed_v2). Its bitstream is built and meets timing at 50 MHz (100 MHz missed by 2.66 ns). The ARM program build and the board run are still to do.
  • To follow one bearing from healthy to failure, re-export modelV2's test rows from a single bearing in time order. This needs modelV2/data/rows.npz, rebuilt by prep.py.
  • Train the Tiny-TPU model on the real Ottawa recordings and rerun the exporter and the board app.
