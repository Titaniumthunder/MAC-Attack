    What to watch, in order

    1. Weight load. B is read one row per cycle, last row first. Each w_load cycle pushes every weight one PE down, so after P cycles PE (k, j) holds B[k][j] and keeps it for the whole pass.
    2. Input skew. A row of A is read as one word and turned sideways: lane k feeds PE row k. Row k waits k extra cycles, so the colours form a diagonal wavefront.
    3. Multiply and add. In each PE, × multiplies the value on the wire coming in from the left by the stored weight, and + adds the partial sum coming in from above. Activations move right one PE per clock; partial sums move down.
    4. Output deskew. Column j waits P − 1 − j cycles at the bottom, so all P values of a C row leave together when out_valid = 1 and are written into the C buffer.

    Why the 2-stage PE still adds the right numbers

    With PIPE = 1 the product goes into a register first and is added one cycle later. Every PE does this, so the partial sum arriving from the PE above is one cycle later too. Both inputs of the adder still belong to the same row of A:

    row i reaches the adder of PE (k, j) at cycle
    s + i + k + j + PIPE  from the left and from above

    Here s is the cycle row 0 enters the array. The only visible change is latency: a row of C leaves 2P − 1 + PIPE cycles after its row of A goes in. The multiply still uses the weight in the same cycle as before, so loading the next tile does not disturb it and the pass length T = M + 3P − 2 stays the same. In the 2-stage view, watch × and + inside one PE: they often light in different colours, because two rows of A are in flight in the same PE.

    What the extra registers buy

    Tclk ≥ tclk→Q + tlogic + tsetup + tunc
    1-stage: tlogic = tmult + tadd
    2-stage: tlogic = max(tmult, tadd)

    A DSP48E1 slice has a register after its multiplier (MREG) and after its adder (PREG), so a 2-stage PE fits in one slice; that is why pe.sv asks for use_dsp. In our Yosys check the default build used 64 DSP48E1, one per PE. The BRAM output register does the same job for memory reads. Together they cost 2 cycles per run: perf_total = perf_cycles + 3 + PIPE + MEM_REG.

    Each register stage also pays a fixed overhead, about 0.42 + 0.566 + 0.154 ≈ 1.14 ns on the path in your 100 MHz report, so each further split gains less than the one before. The RTL uses the same structure at larger P; this picture stops at 4 so the numbers stay readable.
